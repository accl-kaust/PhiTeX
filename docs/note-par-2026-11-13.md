## 2. What the run logs say (accl 28297, observe+profile, PHITEX_RUN_LOG)

### para4000 -j8: the page chain starves behind the text's blocks

A clean build dealt its text as n contiguous blocks, one per worker
(`Engine::evaluate_here`). The page layer folds the text in TeX's order,
so it can follow only the front of the text, and the front was the first
block's, moving at one worker's pace, the same worker that also ran the
page chain (the loop rest, its finisher, the next rest: four runs and four
commits a page). During the 350 ms in which the eight workers ran the text,
the chain fired 45 of the 692 pages. Then it ran alone, 0.78 ms a page on
one or two workers (finisher 0.31 ms, the loop's three steps 0.08 ms, the
rest commits and re-asks), about 500 ms of the 1018 ms span. The
`pdfpage` writers (final-only, unless streaming) and the link make the
last 100 ms.

### amsldoc: three passes, most of -j8's work thrown away

-j1: pass 1 1562 ms (kept text: exec 359 + resume 258 ms; the finishers
of pass 1 are all thrown away), pass 2 460 ms, pass 3 105 ms. -j8: pass 1
1712 ms, busy 6.3 s of which 0.93 s kept. No kept run is in flight for
1.13-1.16 s of the 2.3 s. The reruns: `skind`, `if@nobreak`, `cs:par`,
`count:187`, `toks:12`, `if@newlist`. The text is TeX's own serial chain
of state; its kept runs alone are 0.6 s at -j1, so 0.5x (1.15 s) needs
the chain to run at -j1's speed and nothing else on the critical path.

### Grail: pictures wait for the text chain

-j8: one kept run in flight for 14.6 s of 23.5 s, none for 4.4 s; 50% of
the CPU thrown away. The eight-to-eleven picture children (0.8-1.4 s
each) start only when the text chain reaches their figure, because the
figure's run places them. On a clean build each picture runs twice:
inline in its figure's run (that output is used) and as its child (kept
for the edits after). At -j1 that is 6.1 s of the 19.3 s.

## 3. Step 1, built: the text dealt to every worker at the front

The clean build's text goes in TeX's order to one shared queue
(`Shared::deal`). A worker whose block is empty takes the next few nodes
(`Worker::take_dealt`, `DEAL_RUN` = 4, or an n-th of what was dealt
where that is fewer, so a few nodes go one share to each worker as the
blocks did) into its block and runs them in order. So every
worker works at the front, the page layer folds right behind it, and a
worker busy on the page chain takes fewer text nodes instead of holding
back a block of a sixth of the document. This is the order `Ready` is
meant to give ("on more [threads] the earliest work first, the critical
path's"); the blocks broke it for the text. Runs of four keep a node
after its predecessor on one worker most of the time, which the blocks
were for (a node reads what the one before it defined).

## 4. Step 2, built: a picture child is no hole for the page layer

After step 1, Grail's -j8 timeline (accl 28310) still ran its figures one
after another: each figure's run (the picture read inline, 1.2-1.5 s),
then the picture's child (1.2-1.9 s), then the next figure's text. The
page layer's frontier stood at the child (`frontier: 1256 -> 1310 ... by
1307`) for the child's whole run, and the text after the figure was held
there. The child contributes nothing (its contributions are in its output,
the parent's where the picture stands), but `Pic` did not say so, so
`Ctx::next_contribution` took a child not run yet for a hole. With
`Pic::contributes` false the loop folds past it.

Grail -j8 19.04 -> 15.54 s, -j16 20.03 -> 17.07 s, -j1 unchanged, md5
identical (mc 86231). amsldoc has no pictures and does not move.

## 5. Tried, not merged: a run does not yield to a node that defines nothing

Branch `par1-yield`. In Grail -j8 (accl 28359) the `\paragraph` after a
figure (node 419) stopped ten times, "waits for" the figure's picture
child, and began only once the child had committed:
`Ctx::yield_to_prefix` gives the worker of the run furthest ahead to the
earliest node waiting (`sched::starved_by`) and parks the run until that
node commits, and a picture child's commit changes nothing the text reads.
The experiment: `Pic::may_define` is `MayDefine::Nothing`, and
`starved_by` passes over a node that defines nothing. Same binary, 5 reps
on one node (mc 86270): Grail -j8 18.21 / 18.20 s, -j16 16.04 / 16.60 s,
the spread 15-19.5 s either way. No measured gain, so not merged.

## 7. What still limits, measured, and what would reach the bars

**para4000 (bar met, 3.2x).** What is left at -j8 is the page chain: the
loop rest, the finisher (0.31 ms), the next rest, four runs and four
commits a page, 0.78 ms a page when nothing else runs, about 540 ms for
692 pages; the text's 4804 pieces take about 350 ms on eight workers
beside it. Then the PDF page writers run only once the line is quiet
(`PdfPage::final_only` outside streaming, about 100 ms) and the link
(48 ms) after them. Next: a page's four commits and re-asks
(finisher commit 12-28 us plus re-ask 70-82 us, the rest 50 us) and the
writers as each page ships (the streaming lane's).

**amsldoc (bar not met: -j8 1.17x its -j1).** The time is TeX's own
chain. -j1 is three passes (1.56, 0.46, 0.10 s); pass 1's kept text is
0.62 s of expansion in place order, and every finisher run in pass 1 is
thrown away (the page numbers and references of pass 2 change them). At
-j8 (accl 28405), pass 1 spends 5.9 s of CPU to keep 0.95 s; no kept
run is in flight for 1.1 s of the 2.2 s; the reruns are on `skind`,
`\if@nobreak`, `\par`, `count:187`, `\everypar`, `\if@newlist`: the
state each paragraph leaves to the next. The moonshot's dependence graph
(docs/moonshot on `moonshot`, §1) put amsldoc's run-atomic span at 1031
of its 1127 ms of kept work: there is almost nothing to overlap without
knowing a paragraph's start state before the paragraph before it has run,
and cold value prediction recovers 0-4% of the waste (scaling-2026-11 §8).
What would reach 0.5x (1.15 s): (a) the kept chain at -j1's speed at -j8
(today 1.39 s of kept runs at -j8 against 0.97 s at -j1: clock and the
cores beside it); (b) pass 2 and 3 off the chain: the page layer's
finishers of pass 1 not run until the text has settled (they are 100%
waste), and pass 2's text reruns only where an aux value moved; (c) a
paragraph's start state from the previous build's record (warm), which
the November predictor test put at 84% of refuted reads. (a)+(b) bound
-j8 at about 1.2-1.4 s; only (c) goes past it, and only warm.

**Grail (bar not met: -j8 0.85x its -j1).** The chain now (accl 28405,
-j8): the class load (1.58 s), the preamble, and each figure's float run
reading its picture inline (1.1-1.5 s each, eight figures), held by the
page layer's frontier where they read float state (`\@freelist`). Each
picture's child runs beside it as well, the same work again (6.1 s of
CPU at -j1, the figure's run having already read the picture inline; at
-j1 a third of the build). What would reach 0.5x (9.3 s): the picture
children placed by the hint pass, before the text reaches the figure
(the pictures' bodies are known from the source: `pic::PICS`), each
reading before its placer as today (`Ctx::read_before_placer`), and the
figure's run taking the child's output instead of reading the picture
inline, on a clean build too. The pictures' own reads of text state are
few (the fonts they load first, microtype's font list, pgf's counters:
spec-picture-child §5), so most children would stand once the preamble
has committed, and about 8 s of pictures would leave the chain: Grail
-j8 about 8-9 s. Size: several agent-days, with the font identity of
§5 there.
